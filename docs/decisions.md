- 2026-11-26 (security fix asked for by the platform): a borrowed session is rechecked on every request, whether its token comes in the cookie or an `Authorization` header. A no from `canMasquerade` or the new optional `recheck` deletes the borrowed session and reports `onStop` with `revoked: true`. The check is an auth strategy that always returns no user, placed first on the auth collection, and it skips the stop endpoint so `onStop` is reported once. It fails closed: if the check can't finish, the borrowed token is ignored for that request. The delete reads the sessions again in a transaction, so a sign-in made meanwhile is kept and `onStop` is reported once. Masq now refuses a collection that isn't an auth collection, and a `useSessions` other than `true` or left out: when the config is built, again in `onInit` against the built config (a later plugin or the host can change it), and on every request, where a borrowed token is ignored and start refuses. It also refuses a `readOnly` that isn't a boolean. Stop matches the borrowed claim by user and session id, and with the state cookie present it ends the session only when the claim names the same masquerader and target. Shipped as 0.1.2.
- 2026-11-27 (security fix): start never tells someone who isn't allowed whether a user exists. Someone `canMasquerade` refuses with no target gets one 403 for any id they're refused. Someone it allows with no target gets 404 for a missing user, and for a refused user their own read access doesn't find; 403 only for a refused user they can read. The no-target answer isn't a new requirement for starting: a target the rule allows still starts. A failed lookup is logged and treated as a missing user. Shipped as 0.1.3.
